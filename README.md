# ruvy 검사 콘솔 — 웹 UI/UX 시안

화이트보드 스케치(S/N 입력 → 위치 선택 → 검사 → 결과 → Fail 당시 화면)와 장비 서비스모드 화면·판정 규칙표를 바탕으로 만든 웹 UI 시안입니다.
두 가지 밝은 톤 시안이 있습니다.

| 폴더 | 시안 | 특징 |
| --- | --- | --- |
| `/` (루트) | **시안 B** | ruvy 브랜드. 증권 터미널의 구조 + 토스의 여백과 곡률. 상단 GNB + 상태줄 + 지수 카드 + 한 단 본문 + 하단 티커 |
| `v1/` | ~~시안 A~~ (구버전 보관) | 방향이 정해지기 전의 초기 시안. 장비 일반 화면(Energy·J/shot) 기준이라 지금 설계와 데이터 모델부터 다릅니다 |

두 시안 모두 기능·흐름·데이터 구조는 같고, `index.html`을 브라우저에서 열면 바로 동작합니다. 빌드·설치·외부 네트워크가 필요 없습니다.

> `v1/`은 참고용으로 남겨 둔 **구버전**입니다. 현재 설계는 루트 한 벌뿐이고, 아래 내용은 전부 루트 기준입니다.

## 글 대신 배치와 숫자로

- **제목은 전부 명사**입니다. `S/N 입력` · `위치 선택` · `위치 1 검사` · `검사 결과` · `회차 맵` · `판정 기준`. "…하세요", "…할까요?" 같은 문장 제목은 쓰지 않습니다.
- **배치는 설명하지 않습니다.** 위치 1·2를 나란히, 3을 오른쪽 끝에 두는 것으로 끝입니다. 장비 앞에 서면 같은 모양이 보이니 글로 적을 이유가 없습니다.
- **위치 카드에는 숫자만** 둡니다. Pass/Fail은 결과 화면이 다 보여주므로 여기서 미리 셀 필요가 없습니다. 완료 체크와 얇은 진행 막대만 남겼습니다.

## 모든 화면이 같은 말을 합니다

네 화면이 같은 세 묶음(**Fail · 주의 · OCR 미확인**)과 같은 **1~600 회차 번호**로 말합니다. 어느 화면에서 봐도 숫자가 맞습니다.

| 화면 | 무엇을 말하는가 |
| --- | --- |
| **S/N 입력** | 무엇을 어떻게 볼지 먼저 보여줍니다 — 총 600회 · 서비스모드 26개 항목 · 기준이 있는 13개, 그리고 그 13개의 규칙을 칩으로 |
| **위치 선택** | 숫자 1 · 2 · 3 만. 장비 배치와 같은 자리에 두었으니 글로 설명하지 않고, Pass/Fail은 어차피 결과에서 봅니다. 완료 표시와 진행 막대만 남겼습니다 |
| **검사** | 실시간 회차 맵 + 같은 요약 한 줄 + 최근 Fail. 지수 카드도 `Fail · 주의 · OCR 미확인`로 쪼개 보여줍니다 |
| **결과** | 1–600 회차 맵, 확인이 필요한 회차 번호 목록, 회차 로그 표 |
| **중지 · 완료 확인** | "확인이 필요한 회차가 20회(Fail 7 · 주의 2 · OCR 미확인 11)입니다" — 같은 문장으로 |

하단 티커도 같은 묶음을 답니다.

## 화면 구성

한 단 본문입니다. 오른쪽 현황 열과 아이콘 레일을 없애고 그 폭을 본문이 가져갑니다.

- **상단 GNB** — 왼쪽에 ruvy 로고 + `검사 콘솔` 제품명, 오른쪽에 검색·S/N 칩·단계별 주요 동작 버튼 하나.
- **단계 네비** — 메뉴가 링크 묶음이 아니라 검사 흐름 그 자체입니다. 지나온 단계는 보라 체크, 지금 단계는 채운 알약(번호 원 + 이름), 앞 단계는 흐린 번호. 사이를 짧은 선으로 잇습니다. `결과`에 Fail이 있으면 빨간 배지로 개수가 붙습니다. 지나온 단계는 눌러서 돌아갈 수 있고, 아직 못 가는 단계는 비활성입니다.
  - 1400px 아래로 좁아지면 **지금 단계만 이름을 남기고 나머지는 번호 원으로 접힙니다.** 1200px에서 S/N 칩, 1040px에서 제품명이 빠지고, 820px 아래에서는 로고 / 단계 / 검색+버튼 세 줄로 접힙니다.
- **상태줄** — 띠가 아니라 본문 위의 가벼운 한 줄. 카메라·Edge 연결, 감지 중 여부, 현재 위치·모드, 전체 진행률.
- **지수 카드 4장** — 전체 수집 / Pass / Fail / 평균 신뢰도. 스파크라인은 실제 데이터로 그립니다(누적 수집, 구간별 Pass율, 누적 Fail, 구간 평균 신뢰도).
- **탭 + 필터 칩** — `전체 회차` / `위치·모드별`, 그 옆에 전체·Fail·신뢰도 칩과 Fail 이동.
- **회차 맵** — `전체 회차`에서는 위치·모드별로 한 줄씩, 600회가 여섯 줄로 들어옵니다. 한 그룹만 보면 25칸 × 4줄입니다.
- **항목별 Fail · 위치·모드 · 최근 Fail** — 표 위아래로 나눠 놓았습니다. 전부 눌러서 해당 필터나 회차로 이동합니다.
- **하단 티커** — S/N, 수집, Pass, Fail, Pass율, 평균 신뢰도, 최근 Fail 한 줄 고정.
- **톱바 검색** — 회차 번호, 시각, 읽은 값, 위치·모드, Pass/Fail 어디에 걸려도 찾습니다. 표·회차 맵·항목별 Fail이 함께 좁혀집니다.

### 브랜드

`assets/logo.png`의 ruvy 로고를 GNB에 넣고, **강조색을 로고에서 그대로 뽑았습니다.**

- 보라 `#6454EF` — 흰 바탕 **5.18:1**이라 글자로도, 채움 위 흰 글자로도 AA를 통과합니다. 버튼·활성 상태·진행 막대·포커스 링·수집 스파크라인이 모두 이 색 하나입니다.
- 본문 잉크 `#11121B` — 로고 워드마크와 같은 값입니다.
- 회색 계단도 보라 쪽으로 아주 살짝 기울여(`#f5f5f9` / `#f2f2f8` / `#e8e8f2`) 브랜드와 붙였습니다.
- 초록·빨강·주황은 그대로 판정 상태 전용입니다. 강조색은 여전히 하나입니다.

### 여백과 곡률

[TasteSkill](https://www.tasteskill.dev/)(`npm i taste-skill`)의 `taste-default` + `taste-soft-calm` 규칙을 적용했습니다.

- **간격은 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 스케일에서만** 꺼내 씁니다. 전부 CSS 변수(`--s1`~`--s8`)로 묶었고 매직 넘버가 없습니다.
- **테두리보다 여백과 배경 단차를 먼저** 씁니다. 카드에서 1px 선을 모두 걷어내고 흰 면 + 그림자 한 겹으로 띄웠습니다. 선이 꼭 필요한 표의 행 구분만 7% 농도로 남겼습니다.
- **그림자는 한 겹**, 큰 블러(24px), 6% 농도. 겹쳐 쌓지 않습니다.
- **곡률을 키웠습니다** — 카드 20px, S/N·위치 카드와 다이얼로그 28px, 버튼·입력 12~16px, 칩·탭·검색창은 완전한 알약. 회차 맵 칸도 4px로 둥글렸습니다.
- **배경은 순백이 아니고**(`#f5f5f9`), **글자는 순검정이 아닙니다**(`#11121b`).
- 강조색은 파랑 하나. 초록·빨강·주황은 판정 상태 전용이고 시리즈 색으로 쓰지 않습니다.

한 가지는 skill 권고와 다르게 갔습니다. soft-calm은 본문 굵기 700을 피하라고 하지만, 토스처럼 숫자와 제목은 700으로 뒀습니다. 수치를 빠르게 읽는 화면이라 여기서는 레퍼런스를 따랐습니다.

### 색

증권 UI의 회색 계단과 파랑(#3182F6)·빨강(#F04452)을 쓰되, 색은 눈대중이 아니라 계산해서 정했습니다.

- 본문 글자는 모두 **명암비 4.5:1 이상**입니다. 브랜드 보라는 5.18:1이라 그대로 쓰고, 빨강은 원색이 3.7:1이라 작은 글자에 한 단계 진한 값(#CC1F2E)을 씁니다.
- 회차 맵의 Pass·신뢰도 낮음·Fail 세 색은 **색각 이상에서도 구분되는지 ΔE로 검증**했습니다(deutan 13.6 / 정상 19.5). 원색 초록·빨강 조합은 deutan ΔE 4.6으로 구분이 안 돼 밝기를 벌린 값으로 바꿨습니다.
- 표에서 기준값과 같은 값을 흐리게 처리하되, 그 회색도 4.5:1을 지킵니다.

권장 폭은 1440px 이상입니다. 1280px까지는 표가 가로로 넘치지 않고, 그보다 좁으면 가로 스크롤이 생기되 회차와 P/F 열은 고정되어 따라옵니다. 1180px 이하에서 2단이 1단으로 접힙니다.

## 100회 이상을 한눈에

한 번 검사하면 위치 3곳 × 모드 2개 × 100회 = **최대 600회**가 쌓입니다. 표만 길게 늘어놓으면 스크롤 말고는 볼 방법이 없어서, 아래 다섯 가지로 설계했습니다.

**1. 1–600 회차 맵** — 위 절을 보세요. 한 칸이 회차 하나, 여섯 줄로 600회가 들어옵니다.

**2. 항목별 Fail** — 100회가 넘어가면 "몇 번째 행이 틀렸나"보다 "어느 항목이 계속 틀리나"가 먼저 필요합니다. 기준이 있는 13개 항목 중 어긋난 횟수를 막대로 세워 정렬합니다. 막대를 누르면 그 항목이 어긋난 회차만 남고, 회차 맵도 해당 칸만 남기고 흐려져 어디에 몰려 있는지 보입니다.

**3. 필터** — 기본이 `확인 필요`입니다. `Fail` / `OCR 미확인` / `전체` 로 바꿉니다.

**4. 회차 로그 표** — 26개 값을 옆으로 늘어놓지 않고, 어긋난 항목만 칩으로 요약합니다. 빨강은 기준 벗어남, 주황은 주의 구간, 회색은 신뢰도가 낮은 항목입니다. 행을 누르면 26개 전체 비교표가 열립니다.

**5. Fail 이동** — `Fail 이동 ↑ ↓` 로 Fail 행만 건너뛰며 훑을 수 있습니다.

| screen | 화면 |
| --- | --- |
| `results` → Fail 칩 | 11 · Fail 33회만 |
| `results` → 항목별 Fail 막대 | 12 · 한 항목이 어긋난 회차만 |
| `position-done` | 08 · 위치별 Fail·확인 요약 |
| `results` 아래쪽 | 13 · 확인이 필요한 회차 번호 |
| 번호 클릭 | 15 · 그 회차의 어긋난 항목과 규칙 |
| 톱바 검색 | 14 · 검색어로 좁힌 결과 |

## 감지 항목 — 서비스모드 26개

`assets/device-sample.jpg`(장비 서비스모드 화면) 위에 **26개 항목의 감지 영역(ROI)** 을 그립니다. 좌표는 원본 사진(2000×1500) 픽셀 기준이며 `app.js`의 `FIELDS` 배열에 있습니다. 태그는 이름 대신 `번호 · 값` 으로 줄여 26개가 겹치지 않게 좌·우로 나눠 붙였습니다.

### 판정 규칙

종이에 적힌 원칙을 그대로 옮겼습니다. **기준이 적혀 있지 않은 항목은 임의로 만들지 않고 `기록만`으로 두었습니다.** 26개 중 13개에 규칙이 있습니다.

| # | 항목 | 규칙 |
| --- | --- | --- |
| 3 | RF+ 오차 | `< 100` — 100 이상이면 베이스보드 FET 의심 |
| 4 | RF- 오차 | `< 100` — 100 이상이면 베이스보드 FET 의심 |
| 5 · 6 · 15 | 카트리지 · 베이스보드 · 핸드피스 주파수 | 셋이 **서로 일치**해야 함 |
| 9 | 카트리지 온도 | `40°C` 이상 주의 · `45°C` 이상 에러 |
| 17 | 카트리지 지역코드 | `40` 국내 · `41` E · `42` C · `43` R |
| 18 | 카트리지 셋팅 전력값 | `= 820` (에이징용) |
| 22 | 베이스보드 Fault | `= 0` |
| 23 | 핸드피스 Fault | `= 0` |
| 24 · 25 | 전류센서 1 · 2 | `95~100%` |
| 26 | BB-HP-GUI 통신에러 | `= 0` |

나머지 13개(RF+, RF-, RF 에러, RF 파워 에러, 핸드피스·베이스보드 스테이터스, 내부온도, FAN RPM, 카트리지 시리얼 넘버, 핸드피스 지역코드, 잔여 샷수, 베이스보드 스테이터스2, 카트리지 MAX 파워값)는 값만 기록합니다. 기준이 정해지면 `FIELDS[].rule` 에 한 줄 넣으면 됩니다.

규칙 종류는 `max` / `range` / `eq` / `zero` / `enum` / `band`(주의·에러 2단) / `match`(서로 일치) 일곱 가지이고, 항목 하나라도 벗어나면 **그 회차는 Fail**입니다. 화면 아래 `판정 기준` 카드에 26개 전부가 그대로 나와 있습니다.

## 1 – 600 회차 맵

검사 한 번에 위치 3곳 × 모드 2개 × 100회 = **600회**가 쌓입니다. 26개 항목을 매번 늘어놓으면 볼 수가 없어서, 화면은 **몇 번째 회차가 어떻게 됐는지**만 말합니다.

- **회차 번호는 1~600 통짜**입니다. 위치·모드별 1~100이 아니라 전체를 한 줄로 셉니다(위치1·MP 001–100, 위치1·Normal 101–200 … 위치3·Normal 501–600). 표·티커·상세 어디서나 이 번호로 부릅니다.
- **맵은 한 칸이 회차 하나**, 한 줄이 위치·모드 하나입니다. 여섯 줄이면 600회가 다 들어옵니다. 초록 Pass / 주황 주의 / 노랑 OCR 미확인 / 빨강 Fail. 오른쪽 끝에 줄별 `Fail · 확인` 개수.
- 칸에 올리면 `305번 · Fail · 3. RF+ 오차` 처럼 뜨고, 누르면 그 회차의 당시 화면이 열립니다.

맵 아래에 **번호만 모아 둡니다.** 세 묶음이고 서로 겹치지 않습니다.

| 묶음 | 뜻 |
| --- | --- |
| **기준을 벗어남 (Fail)** | 기준이 있는 13개 항목 중 하나라도 벗어난 회차 |
| **주의 구간** | 에러는 아니지만 기준에 가까워진 회차 (예: 카트리지 온도 40~45°C) |
| **OCR 미확인** | 카메라가 값을 확실히 읽지 못한 회차 — 눈으로 확인이 필요합니다 |

번호를 누르면 그 회차의 당시 화면과 26개 항목 비교표가 열리고, 묶음마다 있는 `이 회차만 보기` 로 표를 그 묶음만 남길 수 있습니다.

**표는 기본이 `확인 필요`** 입니다. 600행을 처음부터 펼쳐 두지 않고, Fail·주의·OCR 미확인만 올려 둡니다. 칩으로 `Fail` / `OCR 미확인` / `전체` 로 바꿀 수 있습니다. 어느 항목 때문이었는지는 아래 `어느 항목 때문인지` 막대에서 봅니다.

## 실제 연결 지점

- `detectFrame(position, mode, i)` — 지금은 시뮬레이션입니다. 카메라 프레임을 `FIELDS[].roi`로 잘라 OCR·디코드한 결과를 `{ key: { v, conf } }` 형태로 반환하도록 바꾸면 됩니다. `v`는 규칙과 비교할 값, `conf`는 OCR 신뢰도입니다.
- `FIELDS[].rule` — 판정 규칙입니다. 기준이 정해지지 않은 13개 항목은 `rule: null`(기록만)로 두었으니 규격이 나오면 채워 주세요.
- `업로드` 버튼 — 서버 전송은 시뮬레이션입니다. `Excel 내보내기`는 CSV(UTF-8 BOM)를 내려받습니다.
